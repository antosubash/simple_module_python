# Issues #929–#933: fresh-app DX follow-ups to 0.0.46

Five bugs found on a fresh 0.0.46 app (`smpy new` → `create-module` → `smpy add`
→ `make dev`). One branch, one PR, one commit per issue.

## Goal & scope

In: the five issues below. Out: #580 (SSR, deferred), and any change to how
modules are discovered at runtime (a restart stays necessary after `smpy add`).

## #929 — plain `uv sync` uninstalls `simple_module_cli`

- Add `simple_module_cli=={{FRAMEWORK_VERSION}}` to the workspace root
  `[dependency-groups] dev` in `templates/workspace/pyproject.toml.tpl`, next to
  `simple_module_test`. `smpy package-update` already rewrites `simple_module_*`
  pins in every dependency group, so updates keep it in step.
- `smpy doctor` without `simple_module_core`: when the cwd is inside an app
  (`find_workspace_root` finds a project), say the `smpy` that ran is not the
  project's (print its version and path) and give the fix (`uv sync --all-packages`,
  then `uv run smpy …`), instead of "run it inside a project".
- Version-mismatch notice: every `smpy` invocation inside an app whose
  pyproject pins `simple_module_cli==X` (or, failing that, `simple_module_core==X`)
  with `X` ≠ the running CLI's version prints one stderr warning naming both
  versions and the executable path. Warning only, never blocks.

## #930 — editing `locales/*.json` doesn't reload under `make dev`

- App template `Makefile` `dev-api`: add `--reload-include '*locales/*.json'`
  (matches module `locales/` and the host's; `Path.match` is right-anchored, so
  `package.json` and the rest are not watched). A reload re-runs the dev boot,
  which regenerates i18n keys.
- Framework repo's own `make dev`: same flag, for parity.
- Fix the Makefile comment that claimed locales already reloaded.
- Existing apps: CHANGELOG entry gives the one-line Makefile edit.

## #931 — no restart hint after `smpy add`

- `smpy add` (after a successful sync): print "If `make dev` is running,
  restart it: modules are discovered at start-up, not on reload." Always, not
  port-probed: a probe adds a failure mode and a stale-port false negative for
  one line of text.
- `create-module` next steps: `uv run smpy add …` (not bare `smpy`); migration
  message uses the same slug as `smpy add`'s hint; drop `make install` if `smpy add`
  already covers it (it runs `uv sync --all-packages`, gen-pages and sync-js-deps;
  if the new npm workspace member still needs `npm install`, print that instead).
- `smpy add`'s migration hint uses the short module name (`add bookmarks`,
  `simple_module_` prefix stripped) to match.

## #932 — `smpy new` hits uv's stale index right after a release

- In `smpy new`'s install phase, when `uv sync` fails, retry once with
  `--refresh`, printing "uv's cached PyPI index may predate this release;
  retrying with --refresh". Only the second failure prints the uv output and the
  manual-setup warning.
- Rejected: always passing `--refresh-package` for every pinned package — ~20
  extra index fetches on every `smpy new`, for a failure that only happens in the
  minutes after a release.
- When the retry also fails (or install is skipped), next steps say
  `uv sync --all-packages --refresh` helps if resolution fails on a just-released
  version.

## #933 — library warnings on every `make migration`, SM026 on every doctor

- `make_process_revision_directives(metadata)` (already called by every app's
  `env.py`, so existing apps get it without a template change) installs
  `warnings.filterwarnings("ignore", …)` for the SQLAlchemy `SAWarning`
  ("Skipped unsupported reflection of expression-based index …") and Alembic's
  `UserWarning` ("autogenerate skipping metadata-specified expression-based index
  …"), narrowed to the expression-index names the metadata declares. The hook
  already re-emits these for new tables and names the ones the database lacks.
- SM026: report only expression indexes whose name the SQLite database does
  not have. Doctor already reads the database for SM010/SM011; extend that read
  (`read_migration_state`) with SQLite index names and pass them to SM026. No
  database reachable → unchanged behaviour (report all). A fresh migrated app
  then shows no SM026. The dev-boot path keeps reporting through the existing
  `_note_unverifiable_expression_indexes` log, filtered the same way.

## Decisions made (override any)

- One PR for all five (they share the CLI and template; previous batches did the same).
- Version-mismatch notice is a warning, not an error.
- `smpy add` restart hint is unconditional.
- `--refresh` on retry, not up front.
- Warning filters live in `simple_module_db`, not the template `env.py`, so existing apps benefit.

## Testing

- Unit: template render contains the cli pin; doctor error text inside/outside an
  app; mismatch notice (pinned ≠ running, equal, no app); `smpy new` retry path
  with a fake runner (fail → refresh → ok; fail twice); `smpy add` output; create-module
  next steps; warning filter (emits nothing for declared names, still warns for
  undeclared); SM026 with and without existing index names.
- Integration: existing scaffold tests (`smpy new` e2e with local sources) still pass.
- Manual: scaffold an app from the branch, `uv sync`, `uv run which smpy`,
  `make migration` output, `smpy doctor`, edit `locales/en.json` under `make dev`
  and see a reload.

## Risks

- Alembic/SQLAlchemy warning text could change; the filter then stops
  matching and the warnings come back (harmless). Tests pin the current text.
- `npm install` may still be needed after `smpy add` for a new npm workspace
  member; verified during implementation before dropping `make install`.
